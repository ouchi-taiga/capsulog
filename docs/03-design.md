## 2. システム構成

```text
[収集バッチ] --日次--> [D1] <--- [SvelteKit] ---> [R2]
     |                          Cloudflare Workers
  各メーカー
GitHub Actions
```

| レイヤ | 技術 | 選定理由 |
|---|---|---|
| アプリ | SvelteKit（adapter-cloudflare） | 画面と API を1つで持つ。PWA化が容易 |
| ホスティング | Cloudflare Workers | 無料枠 10万req/日。帯域は無料 |
| DB | Cloudflare D1（SQLite互換） | 無料枠 5GB |
| 収集バッチ | Python / GitHub Actions | 日次実行。実行時間の上限が緩い |
| 画像（棚） | Cloudflare R2 | ユーザー撮影の切り抜きを置く。無料10GB、egress課金ゼロ |
| 切り抜き | ブラウザ内で実行 | サーバーコストゼロ。生画像が端末から出ない |

全て無料枠に収まる。

**画面と API を分けない。** エンドポイントは3本しかなく、分けると型を手で合わせる手間だけが増える。
SvelteKit の server route から D1 を引き、同じ型定義を画面と共有する。

Vercel を選ばない理由は、Hobby プランが商用利用を認めておらず、課金を始める時点で有料プランに移る必要があること。
D1 に相当するデータベースも別途契約になる。

### 収集バッチを Workers で動かさない理由

**実行時間が収まらない。** 奇譚クラブは商品ごとに詳細ページを取りに行くため、953件を1秒間隔で回すと約16分かかる。5社で約45分。Workers の Cron は CPU 時間に上限があり、この処理は入らない。

**収集は書き捨てに近い。** メーカーが HTML を変えるたびに直す。
Python なら標準ライブラリだけで書け、手元で試しながら直せる。

### Workers の制約

アプリ側には以下の制約がかかる。

- Node.js の API が全て使えるわけではない
- ファイルシステムに書けない
- 1リクエストあたりの CPU 時間に上限がある

D1 にクエリして返すだけのため、これらの制約に当たらない。

## 3. データモデル

テーブル定義は `db/` に置く。

商品は `products`、ラインナップの各種類は `variants`、メーカーは `makers` に持つ。
この3つが商品マスタで、書き込むのは収集バッチと運営だけ。

**ユーザー入力はマスタに入れない。** ユーザーのデータは所有者付きのテーブルに分けて持つ。
ユーザーが何を書いてもマスタが汚れない。

| テーブル | 中身 |
|---|---|
| `user_products` | 自分用の商品。非公開で、本人のカレンダーにだけ合成する |
| `favorites` | お気に入り。入手済みの印を持つ |
| `displays` / `display_cases` / `display_items` | 棚。什器と、その上のケースと写真 |
| `match_entries` | 譲・求 |

什器の種類や素材のマスタテーブルは作らない。
実体は描画（CSS）でコード側にしかないため、DB は `wood` のような文字列の識別子を持ち、CHECK 制約で値を防御するだけにする。

## 4. データソース

### 4.1 5社の比較

収集対象は奇譚クラブ・ターリン・タカラトミーアーツ・Qualia・パレード。バンダイは規約により対象外（6.1）。

| | 奇譚クラブ | ターリン | タカラトミーアーツ | Qualia | パレード |
|---|---|---|---|---|---|
| 件数 | 955 | 616 | 約47/月 | 数百 | 100 |
| 一覧の取得 | サイトマップ | JSON API | 月別カレンダーHTML | HTMLページング | カテゴリHTMLページング |
| 詳細の取得 | HTMLパース | JSON API | HTMLパース | HTMLパース | HTMLパース |
| 発売時期 | ⭕ 旬まで | △ 15%欠損 | ⭕ **週まで** | ⭕ 月まで | ⭕ 旬まで |
| 価格 | ⭕ | ⭕ | ⭕ | ⭕ | ⭕ |
| 全何種 | ⭕ | ⭕ | ⭕ | ⭕ | ⭕ |
| ラインナップ名 | ⭕ **唯一** | ❌ | ❌ | ❌ | ❌ |

**ラインナップ名が取れるのは奇譚クラブのみ。** コンプ率の表示は当面この1社の商品でしか成立しない。

### 4.2 奇譚クラブ

一覧はサイトマップ、中身は詳細ページの2段構え。

| 段 | 取得元 | 得られるもの |
|---|---|---|
| 1 | `/products-sitemap.xml` | 全商品のスラッグ（= `source_id`） |
| 2 | 各詳細ページのHTML | 商品名、発売月、旬、価格、全何種、ラインナップ名 |

**WP REST API は使わない。** ホスティング（XSERVER）が海外 IP からの `/wp-json` を遮断しており、
GitHub Actions のランナーから届かない。サイトマップと HTML は世界に配信されている。

詳細ページの構造:

```html
<dl class="c-productDetail__detail-item">
  <dt>発売日</dt><dd>2026年9月下旬</dd>
</dl>
<dl class="c-productDetail__detail-item">
  <dt>価格</dt><dd><span>1回500円</span>　<span>全5種</span></dd>
</dl>
<p class="c-productDetail__pickup-text">グミッツェル グレープ</p>
```

`pickup-text` にはラインナップ以外の説明画像が混ざる。`total_variants` の件数だけ先頭から採用する。

発売日にはまれに「2月上旬」のような年なし表記がある。
今日から過去3ヶ月〜未来8ヶ月に収まる年を補い、生値は `release_raw` に残す。

2010年の商品まで同一構造で、16年分にわたって崩れがない。

### 4.3 ターリン

Strapi の公開APIで、認証なしで全件返る。ページングは `_limit` と `_start`（Strapi v3 系の記法）。

| 用途 | エンドポイント |
|---|---|
| 件数 | `/api/products/count` |
| 一覧 | `/api/products?_limit=100&_start=0` |
| 詳細 | `/api/products/{id}` |

一覧には価格と発売月が含まれないため、詳細を個別に取る。

| 項目 | 取得元 |
|---|---|
| 価格 | `price`（数値） |
| 全何種 | `kind`（数値） |
| 発売月 | `description` の先頭行「2026年6月発売」 |

`kind` はフィールド名からは種類数と読み取れないが、詳細ページの「4種類」と一致する。

**発売月が記載されていない商品が約15%ある。** 詳細ページにも記載がなく、データ側の欠落。NULLとして扱う。割合は時期により変動する。

**サーバが中間証明書を配信していない。** リーフ証明書を2枚返す設定で、ブラウザは補完するがHTTPクライアントからは検証に失敗する。GlobalSign RSA OV SSL CA 2018 を CA バンドルに追加して解決する。

### 4.4 タカラトミーアーツ

月別カレンダー `/items/gacha/calendar/?ym=YYYYMM` が全件の入り口。2000年2月まで遡れる。

カレンダーは「9月7日週発売」という**週単位の見出し**で商品をグルーピングしている。
`release_precision = 'week'` はここから取る。

価格・発売時期（月）・全何種は詳細ページ `/items/item.html?n={ID}` から取る。

```text
■価格:300円(税込) ■発売時期:2026年9月 … 全7種
```

注意点が2つある。

- カレンダーには再販が混ざる。詳細の発売時期が過去の月になっている商品がそれ
- 一部の商品は特設ページへ302リダイレクトされ、項目が取れない。NULL のまま登録する

### 4.5 Qualia

一覧は `/product/index/{page}` のページング、詳細は `/product/view/{id}`。

詳細が dt/dd で構造化されており、商品名・発売日（月）・価格・全何種が確実に取れる。
probe では12件中欠損ゼロ。

### 4.6 パレード

プライズも扱う会社のため、一覧はカプセルトイのカテゴリに絞る。
`/products/products-category/capsule-toy` をページングでたどり、詳細ページをパースする。
最終ページの次は404が返る。これがページングの終わりの合図になる。

詳細ページの構造:

```html
<p class="product-release-month">2026年8月下旬より順次発売予定</p>
<h1 class="product-title">映画ちいかわ たべものいっぱいマスコット</h1>
<ul class="product-notes">
  <li>種類：全7種（内シークレット1種）</li>
  <li>価格：500円</li>
</ul>
```

**発売時期は過半数が年なしの表記になる。** 「3月中旬から順次展開予定」のように月から始まる。
一覧が発売の新しい順に並ぶため、前後にある年付きの商品に挟まれた範囲から年を決める。
並びには乱れがあり、順に足し引きすると古い商品を前年に落としてしまう。

### 4.7 バンダイ

**収集しない。** ガシャポンオフィシャルサイト利用条件が、自動化された手段による掲載情報の取得を事前許諾なく禁じている（6.1）。

商品を載せる場合は運営が手で入力する。`products.origin` で収集分と区別する。
ユーザーはマッチング用のフリーテキストでバンダイ商品を扱える。

### 4.8 対象外

| メーカー | 理由 |
|---|---|
| ケンエレファント | 一覧は公式サイトだが詳細が EC ストアに飛ぶ。EC の収集は規約リスクが別枠になる |
| ブシロードクリエイティブ | WP API はあるが約1万件の全グッズが混在。カプセルトイだけを切り出すカテゴリがない |
| エポック社 | カプセルトイ専用の一覧ページが公式サイトにない |
| SO-TA | 公式ドメインを特定できない |

## 5. 収集バッチ

### 5.1 動作

| 項目 | 仕様 |
|---|---|
| 実行環境 | GitHub Actions |
| 実行頻度 | 日次1回 |
| リクエスト間隔 | 1秒以上 |
| User-Agent | サービス名と連絡先を含む識別可能なもの |
| 失敗時 | ログを残して次のソースへ継続。1社の失敗で全体を止めない |
| 差分検知 | `content_hash` を比較し、変化があるものだけ更新 |

### 5.2 初回と日次の使い分け

初回は5社で約55分かかる。タカラトミーアーツは直近1年分を取る。

日次実行では一覧を取得し、新規と発売が2ヶ月以内に迫った商品だけ詳細を取り直す。
発売済みの商品は変わらないため見に行かない。
取り直した中で `content_hash` が前回と変わったものだけ書き込む。

### 5.3 出典の保持

`official_url` は必須。表示時に必ず公式ページへリンクする。これは利便性ではなく、出典明示という法的要請による。

### 5.4 破損の検知

外部サイトの仕様変更で収集は必ず壊れる。壊れ方は3種類あり、危険度が違う。

| 壊れ方 | 検知 | 危険度 |
|---|---|---|
| APIが404や500を返す | 例外で即わかる | 低 |
| HTMLのクラス名が変わる | パース結果が空になる | 中 |
| **構造が微妙に変わり、間違った値が入る** | **何もしなければ気づかない** | **高** |

3つ目が本当の脅威。エラーは出ず、DBに嘘のデータが静かに溜まる。これを防ぐため、**取り込む前に2段階で検証し、通らなければそのメーカーの取り込みを中止する。**

**件数の異常検知**

前回の取得件数と比べて **30%以上減っていたら中止**する。DBは上書きしない。

一覧の取得自体が壊れると件数が激減するため、最も安く効く防御になる。
全件が一覧に載るメーカー（奇譚クラブ・ターリン・パレード）だけで判定する。
タカラトミーアーツはカレンダーの窓、Qualia は先頭ページしか見えないため対象外。

**値の妥当性検証**

| 項目 | 妥当な範囲 |
|---|---|
| 価格 | 100〜2,000円 |
| 全何種 | 1〜30 |
| 発売月 | 過去30年〜未来2年 |
| 商品名 | 空でない |

範囲外が **全体の10%を超えたら中止**する。単発の外れ値はメーカー側の実データの揺れなので許容する。

`release_year_month` の欠損はターリンで常時8%発生するため、欠損そのものは異常として扱わない。ただし**欠損率が前回から20ポイント以上悪化した場合は中止**する。この判定は全件を見ないと意味がないため、全件モードのみで行う。

**中止したときの動作**

| 対象 | 動作 |
|---|---|
| そのメーカー | 取り込みを中止し、DBは前回の状態を保つ |
| 他のメーカー | 通常どおり続行する |
| ログ | 中止の理由と、判定に使った数値を記録する |

通知はフェーズ1では作らない。開発者自身が毎日使う前提のため、ログを見れば足りる。ユーザーが増えてから追加する。

### 5.5 検証スクリプトによる早期発見

`probe/` のスクリプトは、収集バッチとは独立に各メーカーの構造が生きているかを確認する。
バンダイのものは規約により実行しない。記録として残すだけ。バッチ本体と実装を共有しないため、**バッチ側のバグと外部サイトの変更を切り分けられる。**

収集が中止されたとき、まずこれを走らせて原因がどちら側かを判断する。

## 6. 法的な扱い

### 6.1 各社の規約

| メーカー | 規約 | 自動取得の禁止 | 複製・転載 |
|---|---|---|---|
| 奇譚クラブ | プライバシーポリシーのみ | なし | 記載なし |
| ターリン | プライバシーポリシーのみ | なし | 記載なし |
| タカラトミーアーツ | サイトポリシー | なし | 「無断で転用、転載することはご遠慮ください」 |
| Qualia | 規約ページなし | なし | 記載なし |
| パレード | 規約ページなし | なし | 記載なし |
| バンダイ | ガシャポンオフィシャルサイト利用条件 | **あり** | 掲載情報の使用を事前許諾なく禁止 |

**バンダイは収集対象にしない。** 利用条件が自動取得を明示的に禁じている。

> 自動化された手段（自動ツール・プログラム・ロボットなどこれらに準ずる手段）を用いて
> 掲載情報を取得/使用することはバンダイの事前許諾がない限り、禁止いたします。

違反時は予告なくアクセス遮断を行うと明記されている。

robots.txt はターリンと Qualia が404（存在しない）、奇譚クラブとパレードは `Disallow: /wp-admin/` のみ、タカラトミーアーツは Disallow 記載ゼロ。商品ページを禁じる社はない。

**robots.txt が無いことは許可の明示ではない。** 存在しない場合も1秒間隔を守る。

### 6.2 遵守事項

- 収集するのは事実情報のみ（商品名・発売時期・価格・全何種・メーカー名）。これらに著作権は発生しない
- **商品説明文を保存・表示しない。** 各社の複製禁止条項に該当する
- 画像を自前で配信しない
- 必ず出典を明示し、公式ページへリンクする
- X（旧Twitter）の投稿は機械収集しない。利用規約がAPI外の自動収集を明確に禁じており、著作権法以前に契約違反となる

著作権法30条の4により、情報解析目的の収集は適法。

収集対象の5社が禁じているのは複製・転載までであり、取得そのものではない。
事実情報だけを扱う限り抵触しないが、説明文や画像に手を出した時点で抵触する。

**取得を禁じている社からは取らない。** 規約に自動取得の禁止があれば、対象から外す。

規約は予告なく変更される。**規約とrobots.txtは半年に1度再確認する。**
バンダイのように、後から自動取得の禁止条項が加わることがある。

### 6.3 画像の扱い

商品画像は全社とも版権キャラクター画像であり、再配布はライセンス上の問題が生じる。

| 案 | 判断 |
|---|---|
| ダウンロードして自サーバーから配信 | ❌ 転載にあたる |
| 公式画像URLを直接参照（ホットリンク） | ❌ 著作権侵害には当たらないが、各社が掲示を禁じている |
| **画像を出さず、商品名と公式リンクのみ** | ⭕ **フェーズ1はこれ** |
| ユーザー撮影の写真 | ⭕ **棚はこれ。** 撮影者に著作権があり、規約で利用許諾を得られる |
| メーカーに個別許諾を取る | 理想だが実績のない段階では難しい |

**メーカーに聞いても許諾は出せない。** タカラトミーアーツが明記している通り、
メーカー自身が権利者から許諾を得て使っている立場のため、又貸しにあたる。

`image_url` はDBに保持するが配信しない。画面に出る写真は棚のユーザー撮影のみ。

画像がない分の情報量は、ラインナップ名とタイポグラフィで補う。

## 7. カレンダー

### 7.1 検索と絞り込み

- 検索は商品名の LIKE で行う。現状約2,000件で全文検索は要らない。増えたら SQLite の FTS5 に切り替える
- 版権名（「ちいかわ」等）の専用軸は持たない。商品名にほぼ必ず含まれるため、名前検索が実質の版権検索になる
- 絞り込みは発売月・メーカー・価格帯、ソートは発売時期・価格。いずれも既存の列で足りる
- 絞り込みと検索の状態は URL のクエリパラメータに持つ。結果をそのまま共有できる

### 7.2 お気に入りとリマインド

お気に入りは `favorites` に持ち、入手済みの印を付けられる。入手済みは撮影（棚）への導線になる。

リマインドは **iCal（ICS）フィードの配信**で実現する。
ユーザーごとの購読 URL を1本用意し、お気に入り商品の発売月を予定として返す。
端末の標準カレンダーが取り込みと通知を行うため、サーバは ICS テキストを返すだけでよい。

Web Push は使わない。iOS ではホーム画面に追加した PWA でしか動かず、摩擦が大きい。

### 7.3 自分用の商品

マスタに無い商品（バンダイ等）は `user_products` に登録できる。

- 非公開。本人のカレンダーにだけマスタと合成して表示する
- マスタ（`products.origin = 'manual'`）は運営が入れる公開データ用で、これとは別物

## 8. 棚

### 8.1 切り抜き

ブラウザ内で完結させる。`@imgly/background-removal`（ONNX Runtime WASM）で背景を除去し、切り抜いた PNG だけを R2 に上げる。

- サーバーで画像処理をしない。Workers の CPU 制限に当たらず、コストもゼロ
- 生の撮影画像がユーザーの端末から出ない
- 初回はモデルのダウンロードが入る。読み込み中の表示を用意する

自動で完璧を狙わない。**撮影ガイド（無地の背景・正面）で品質を底上げし、失敗したらブラシで手動リタッチする**逃げ道を必ず持つ。

### 8.2 什器のモデル

什器は `displays` に持つ。1行が1つの棚やボードで、名前を付けて複数保存できる。

| 属性 | 値 | 意味 |
|---|---|---|
| かたち | `shelf` / `pegboard` / `cork` | 棚・有孔ボード・コルクボード |
| 素材 | `clay` / `wood` / `steel` | 棚の見た目。かたちが棚のときのみ |
| マス目 | `1111/1000/…` | どのマスが有効か。かたちが棚のときのみ |

**棚の形はマス目の集合で表す。** 横3段・L字・格子・ひな壇は、有効なマスの並びの違いでしかない。
形のテンプレートはコード側の定数で、選んだ後にマスを個別に増減できる。

什器・素材・ケースの見た目はすべて CSS のグラデーションで描く。**画像素材を使わない。**
種類を足すときは、コードに描画と識別子を足し、CHECK 制約を広げる。

### 8.3 配置

置いた写真は `display_items` に持つ。アクリルケース（`display_cases`）に入れて、シリーズをまとめられる。

| 什器 | 位置の持ち方 | 操作 |
|---|---|---|
| 棚 | マス番号 + マス内の位置 | ドロップすると最寄りのマスに吸い付く |
| ボード | 自由な x, y | どこにでも掛けられる |

物理シミュレーション（積み重ね・傾き・衝突）と 3D 表現はやらない。実装が一段重くなり、飾って共有する価値に寄与しない。

### 8.4 共有

棚の共有画像を生成して X に投稿できるようにする。これが拡散の主導線になる。

棚のアイテムは商品マスタに任意で紐付けられる。紐付いたアイテムはフェーズ2のマッチングが厳密に効く。

## 9. 交換マッチング

### 9.1 データの分離

譲・求は `match_entries` に持ち、商品マスタには書かせない。1件の登録は次のどちらかの形を取る。

| 形 | 中身 |
|---|---|
| マスタ参照 | `product_id` / `variant_id` を持つ。入力時のインクリメンタル検索で選ばせる |
| フリーテキスト | `free_text` を持つ。マスタに無い商品（バンダイ等）の逃げ道 |

### 9.2 マッチの二段構え

```text
1. product_id / variant_id 同士 → 厳密一致
2. free_text が絡むもの      → 曖昧一致で候補を提示
```

曖昧一致は自動で確定しない。「同じものかも」と提示し、確定するのは人。交換は最後に現物を確認して手渡すため、候補の精度を追い込む必要がない。

曖昧一致の実装は段階を踏む。

| 段階 | 手法 |
|---|---|
| 最初 | NFKC 正規化・カナ統一・記号除去した `normalized_text` の部分一致と n-gram の重なり |
| 次 | Workers AI のテキスト embedding + Vectorize |
| 将来 | 画像類似。出品写真の重複検知にも流用する |

### 9.3 エリア

ユーザーは「行ける場所」（駅・店舗・市区町村）を複数登録する。エリアが重なる人同士だけをマッチ対象にする。

GPS の生座標は保存しない。リアルタイムの現在地マッチはユーザー密度が要るため、初期は作らない。

### 9.4 マッチ成立後

登録時に同意済みの X ハンドルを相互開示し、以降のやり取りは X 上で行う。

**アプリ内チャットは作らない。** 1対1のクローズドチャットは電気通信事業法の「他人の通信の媒介」に該当し、届出対象になり得る。公開の出品一覧と運営からの一方向通知は媒介に当たらない。必要になったら届出してから追加する。

X ハンドルは個人情報として扱う。開示はマッチ成立時のみ・相互同意で行い、プライバシーポリシーに明記する。
